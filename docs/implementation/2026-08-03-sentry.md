# Observabilidade Sentry (GlitchTip)

> Status: stable
> Spec: [docs/specs/2026-08-03-sentry.md](../specs/2026-08-03-sentry.md)
> Backend: `src/instrument.ts` · `src/sentry/`
> Guia operacional: [docs/GUIA-GATEWAY.md](../GUIA-GATEWAY.md) §10

## 1. Overview

O gateway instrumenta erros, rastros e métricas com `@sentry/nestjs` 10.69
apontado para a instância GlitchTip self-hosted (`http://31.97.27.185:30808`,
projeto `2`).

Comportamentos-chave (extraídos do código):

- `src/instrument.ts` é o **primeiro** import de `src/main.ts` e executa
  `Sentry.init(construirOpcoesSentry(process.env))` como efeito de import — a
  auto-instrumentação OpenTelemetry só patcheia http, express, pg, ioredis,
  amqplib e Nest se instalada antes do `AppModule`.
- `construirOpcoesSentry` é pura (env → `NodeOptions`): DSN de `SENTRY_DSN` com
  fallback para `DSN_GLITCHTIP_PADRAO`; `enabled: false` quando
  `SENTRY_ENABLED=false` ou o DSN é string vazia; `environment` = `ENV`;
  `release` = `SENTRY_RELEASE`; `sendDefaultPii: false`; tags iniciais
  `servico=whiz-gateway` e `instancia=$HOSTNAME`.
- Amostragem por `tracesSampler` (não por `tracesSampleRate`, que seria
  ignorado se ambos existissem): `1` para `whiz.metrics.snapshot`, `0` para
  `/health`, `/docs`, `/ui`, e `SENTRY_TRACES_SAMPLE_RATE` (default `0.01`) no
  resto. A rota é extraída de `normalizedRequest.url` ou do sufixo do nome da
  transação (`POST /webhook`).
- Sinais não ingeridos pelo GlitchTip ficam desligados: a integração
  `ProcessSession` é removida das default integrations e a `httpIntegration` é
  reinstalada com `trackIncomingRequestsAsSessions: false`; `enableLogs` e
  `enableMetrics` seguem `SENTRY_ENABLE_LOGS`/`SENTRY_ENABLE_METRICS` (default
  `false`).
- `beforeSend` (`escrubarEventoSentry`) substitui, case-insensitive,
  `authorization`, `x-api-key`, `x-hub-signature-256`, `x-meta-access-token` e
  `x-callback-secret` por `[Filtered]`.
- `SentryService.capturarExcecaoHttp` decide o que virá issue: `>= 500` →
  `captureException` (`level: error`); `401`/`403` em rota que começa com
  `/webhook` → `captureMessage` (`level: warning`); demais `4xx` → nada. Todas
  as chamadas levam as tags `rota`, `metodo`, `status`.
- `GlobalExceptionFilter` delega ao `SentryService` antes de responder (status e
  corpo inalterados) e passa `MARCADOR_SENTRY_IGNORAR` no próprio log de erro.
- `SentryWinstonTransport` (transport adicionado ao Winston do `LoggerService`)
  emite breadcrumb para todo log e `captureMessage(level='error')` para logs de
  nível `error` **sem** o marcador — é assim que falhas que nunca viram exceção
  HTTP (consumidor da DLQ, `handle()` do dispatch, jobs de limpeza) chegam ao
  GlitchTip.
- `criarTransportDeLogsSentry()` instala o transport **oficial** de Sentry Logs
  (`createSentryWinstonTransport`) com `levels: ['info','warn','error','fatal']`
  — alimenta a página *Logs* do GlitchTip. O SDK só emite envelope quando
  `enableLogs` está ligado, então o transport fica sempre instalado. Cada campo
  do metadado do winston vira atributo do log; a mensagem vai como texto (o
  `format.json()`/`format.colorize()` afeta só a saída de console, porque o
  winston guarda a linha formatada em `Symbol.for('message')`).
- Log de nível `error` produz **duas** coisas no GlitchTip com logs ligados: a
  issue (agrupa, deduplica, alerta) e a linha de log (contexto navegável,
  correlacionada ao rastro pelo `trace_id`). É intencional.
- `LoggerService` só anexa `optionalParams` ao metadado quando há parâmetros —
  array vazio viraria atributo em todo log.
- `SentryHttpMetricsInterceptor` (`APP_INTERCEPTOR`) conta
  `gateway.http.requisicao` (`rota`, `metodo`, `classe_status`) e registra
  `gateway.http.duracao`, tanto no caminho de sucesso quanto no de erro; a rota
  usa o padrão do express (`/inboxes/:id`) para não explodir cardinalidade.
- `DispatchHandlerService` registra `gateway.despacho.{tentativa,sucesso,falha,
  duracao}` e `gateway.dlq.enfileiramento` (por `StatusFalhaMensagem`) — o
  enfileiramento passou a ser centralizado no helper privado `enviarParaDlq`.
- `SentryMetricsService` acumula contadores e distribuições em memória por
  janela (chave = `nome|attr=valor,...`), no máximo
  `MAX_AMOSTRAS_POR_DISTRIBUICAO` (500) amostras por distribuição — o `total`
  guarda a contagem real. A cada minuto (`@Cron(EVERY_MINUTE)`),
  `emitirSnapshot()` troca a janela e abre
  `startNewTrace → startSpan('whiz.metrics.snapshot', forceTransaction)` com
  `contador.<chave>`, `dist.<chave>.{total,p50,p95,max}` e
  `gauge.processo.{rss_bytes,heap_usado_bytes,uptime_s}`.
- Nenhuma falha do SDK propaga: cada chamada é protegida e degradada a
  `Logger.warn`. Sem cliente inicializado (sem DSN), tudo é no-op — inclusive na
  suíte de testes.
- `SentryModule` (`@Global`) importa `SentryModule.forRoot()` do
  `@sentry/nestjs/setup` (nomes de transação por rota) e faz
  `Sentry.flush(2000)` em `onApplicationShutdown`; `main.ts` chama
  `app.enableShutdownHooks()`.

## 3. Envs

`SENTRY_DSN` · `SENTRY_ENABLED` · `SENTRY_TRACES_SAMPLE_RATE` ·
`SENTRY_ENABLE_LOGS` · `SENTRY_ENABLE_METRICS` · `SENTRY_RELEASE` — todas
opcionais, validadas em `src/config/config.validation.ts` e documentadas em
`.env.example` e `docs/GUIA-GATEWAY.md` §9.

`SENTRY_ENABLE_LOGS` e `SENTRY_ENABLE_METRICS` têm **default `false`** no código
de propósito: o DSN padrão aponta para o projeto de produção, então um dev
rodando local sem env não despeja logs lá. Em produção as duas ficam `true`
(overlay `overlays/whiz-gateway/production` do repo argo).

## 4. Testes

Unitários (`src/sentry/*.spec.ts`, `src/logger/logger.service.spec.ts` + specs
atualizados de `global-exception.filter`, `dispatch-handler.service` e `config`)
cobrem AC-1..AC-20. Não há AC `[e2e]`: nenhum contrato HTTP muda e o SDK fica
desabilitado sem DSN, então um e2e não observaria nada além dos unitários.

Verificação de runtime feita fora da suíte (DSN apontado para porta fechada,
sem tráfego para o GlitchTip): cliente inicializado, `ProcessSession` ausente da
lista de integrações, `Http`/`Express`/`Postgres`/`Redis`/`Amqplib`/`Nest`
presentes, `tracesSampler` devolvendo `0.01`/`0`/`1` e `beforeSend` filtrando
`Authorization`.

## 5. Divergências em relação à spec

- **Correção de premissa (2026-08-04):** a primeira versão desta feature assumia
  que o GlitchTip não ingeria logs. A instância roda `glitchtip/glitchtip:6.2.2`
  e ingere logs estruturados por padrão (`GLITCHTIP_ENABLE_LOGS`), então
  `SENTRY_ENABLE_LOGS` deixou de ser um flag "para o futuro" e ganhou emissor
  (FR-19). Trace metrics segue sem ingestão documentada — `enableMetrics=true` em
  produção é experimento; se os números não aparecerem, o caminho válido continua
  sendo a transação `whiz.metrics.snapshot`.
- A spec cita `autoSessionTracking: false` como o desligamento de sessões
  (assim estava no pedido original). Essa opção **não existe** no SDK v10 — foi
  removida na v9. O equivalente implementado é remover a integração
  `ProcessSession` e passar `trackIncomingRequestsAsSessions: false` à
  `httpIntegration`.
- `Integration` e `TracesSamplerSamplingContext` não são re-exportados por
  `@sentry/nestjs`; os tipos `Integracao` e `ContextoAmostragem` são derivados
  de `NodeOptions` para não adicionar `@sentry/core` como dependência direta.
- `GlobalExceptionFilter` recebe `SentryService` como terceiro parâmetro **com
  default** (`new SentryService()`), porque o filtro é instanciado à mão em
  `main.ts` e em vários specs de integração; o default mantém a captura ativa
  sem exigir mudança em todos os call sites.

## 6. Pendências

- Migrar o DSN para `https` quando o GlitchTip tiver certificado (hoje o
  envelope trafega em claro na rede interna).
- Confirmar na UI se o GlitchTip 6.2.2 ingere trace metrics
  (`SENTRY_ENABLE_METRICS=true` já está ligado em produção). Se ingerir, o
  snapshot de transações pode ser desligado; se não, voltar a env para `false`
  para poupar egress.
- Mensagens de log são strings já formatadas (`HTTP 500 ON POST | /webhook - …`):
  a busca full-text do GlitchTip funciona, mas atributos estruturados
  (`id_inbox`, `rota`, `status`) dariam filtro melhor. Passar metadado em vez de
  interpolar é uma melhoria incremental por call site.
- Propagação de trace gateway → whiz-server (`sentry-trace`/`baggage`) exige
  Sentry no server; fora de escopo.
